# مراجعة جاهزية مآل وفق AgentX

تاريخ المراجعة: 15 أكتوبر 2026

## الحكم التنفيذي

**التقييم الداخلي: جاهز للمنافسة مع مخاطر متبقية.**

مآل يثبت الرحلة الأساسية تقنيًا: بيانات منشأة موثقة من ملفات، مصادر NCA وSASO الحية، حفظ نسخ وبصمات، فلترة توافق، مراجعة ملف مع موضع دليل، تتبع أثر، ثم قرار بشري. أكبر المخاطر قبل Pilot حقيقي هي التخزين المؤقت في Render Free، وعدم وجود SSO مؤسسي أو worker مستقل، ومحدودية تقييم الملفات التي لا تتضمن إحالات أو أدلة قابلة للمطابقة.

## المستخدم والمشكلة والقيمة

- المستخدم الأساسي: موظف الامتثال أو الشؤون القانونية الذي يجمع التغييرات ويثبت أثرها على ملفات المنشأة.
- المشتري المحتمل: إدارة المخاطر والامتثال أو الأمن السيبراني أو الجودة في منشأة متوسطة أو كبيرة.
- المشكلة: العمل اليدوي يفصل بين النص التنظيمي، ملفات المنشأة، مالك الإجراء، والقرار البشري؛ ما يجعل تتبع الدليل بطيئًا وصعب التدقيق.
- القيمة: تحويل المصدر الرسمي إلى نتيجة مرتبطة باسم الملف وموضعه والاستشهاد والإجراء، دون تنفيذ قرار مؤثر قبل اعتماد بشري.
- أقوى فارق: سلسلة أثر محفوظة وقابلة للتدقيق من التشريع إلى موضع محدد داخل مستند المنشأة، وليست مجرد محادثة أو ملخص.

## مراجعة الأمن والصلاحيات

### مطبق

- أول تشغيل ينشئ مديرًا واحدًا ثم يمنع إعادة الإعداد.
- كلمات المرور مخزنة باشتقاق PBKDF2 مع salt مستقل.
- رموز الجلسات عشوائية؛ قاعدة البيانات تحفظ بصمتها فقط، وتنتهي بعد 12 ساعة.
- `admin`: إدارة المستخدمين، اعتماد ملف الشركة، حذف الملفات، وقرار المراجعة البشرية.
- `analyst`: قراءة البيانات، رفع الملفات، تشغيل المراجعة والمسح، دون اعتماد أو حذف أو إدارة مستخدمين.
- كل endpoint حساس يفرض الدور في الخلفية؛ إخفاء الزر في الواجهة ليس آلية الحماية الوحيدة.

### متبقٍ للإنتاج

- لا يوجد SSO/MFA أو استرجاع كلمة مرور أو سياسة قفل محاولات.
- SQLite وsession storage مناسبان للنموذج الأولي/Pilot محدود، لا لنشر مؤسسي متعدد النسخ.
- يلزم TLS وإدارة أسرار وتدوير جلسات ومراجعة أمنية خارجية قبل بيانات حساسة فعلية.

## وضوح نتيجة الامتثال

نتيجة مراجعة الملف تعرض الآن:

1. اسم ملف المنشأة.
2. الموضع الدقيق: سطر، صفحة، قسم/فقرة، شريحة، أو ورقة/خلية.
3. النص الموجود في الملف.
4. المادة والنص التنظيمي الحالي.
5. حالة التوافق والتفسير.
6. التصحيح المقترح.

إذا لم توجد إحالة أو أدلة كافية، يجب أن تكون النتيجة `Needs Review` أو `Insufficient Evidence`، لا مخالفة مختلقة.

## خطة الأولويات

### P0 - قبل العرض

- تشغيل سيناريو معروف كاملًا بعد النشر: مدير → موظف → ملفات منشأة → مسح → مراجعة ملف → موضع مخالفة → اعتماد.
- الاحتفاظ ببيانات عرض احتياطية موسومة بوضوح إذا تعذر المصدر الحي.
- التأكد أن قاعدة Render لم تُمسح قبل العرض، أو استخدام تخزين دائم.

### P1 - Pilot

- PostgreSQL وobject storage وbackground worker.
- SSO/MFA وسجل تغييرات المستخدمين ومحاولات الدخول.
- مجموعة تقييم عربية/إنجليزية تشمل ملفات لا تحتوي إحالات صريحة.
- قياس: زمن اكتشاف التغيير، نسبة النتائج ذات الاستشهاد الصحيح، نسبة Needs Review، وزمن إغلاق المهمة.

### P2 - لاحقًا

- تكامل Odoo/GRC بعد اعتماد المهمة.
- إدارة دورة حياة المستخدمين وتغيير كلمة المرور.
- مقارنة منافسين ومقابلات عملاء موثقة؛ دون ادعاء بيانات غير مقاسة.

## سيناريو العرض المقترح

1. تسجيل الدخول كموظف لإظهار حدود الصلاحية.
2. رفع ملف مشروع أو سياسة يحتوي متطلبًا قديمًا.
3. إظهار اسم الملف والسطر/الصفحة والنص غير المتوافق والاستشهاد الحالي.
4. إظهار مسار الأثر حتى الإدارة والمشروع.
5. محاولة الاعتماد كموظف وبيان أنها غير مسموحة.
6. تسجيل الدخول كمدير، مراجعة المهمة وتعديلها أو اعتمادها مع تعليق.
7. فتح سجل التدقيق لإثبات هوية المنفذ والوقت والقرار.

## ما يجب عدم ادعائه

- لا يُدّعى أن كل غياب لنص داخل ملف يعني عدم امتثال.
- لا تُعرض قيمة ثقة النموذج كاحتمال صحة.
- لا يُدّعى أن Render Free يوفر تخزينًا دائمًا أو توفرًا إنتاجيًا.
- لا يُدّعى تكامل Odoo حي قبل بناء المحول واختباره.
- لا يُدّعى أن جميع الأنظمة السعودية مغطاة؛ الموصلات الحية الحالية NCA وSASO فقط.
